## 1. What this project is

A **Telegram → Interactive Brokers signal trade copier** for options.

Two ways an order gets created:
1. **Signal path** — Telethon listens to a Telegram channel → OCRs the signal image
   (Google Vision, Tesseract fallback) → parses ticker/type/strike/expiry/price →
   sends the user a summary → *Confirm* → user types `price qty` → order placed.
2. **Manual path** — user types an order in chat, either one-line
   (`buy tsla c500 0605 1.8 2`) or step-by-step (`buy` → guided prompts).

Plus: live bid/ask at confirmation, open-position closing, pending-order
cancel/modify, web-based broker login, and gateway auto-recovery.

## 3. Architecture — the three-thread model

```
PTB event loop (main)      ← all Telegram handlers, all user_data
ib_insync calls            ← each runs in its OWN thread + OWN event loop (short-lived connect/disconnect)
Telethon listener          ← its OWN daemon thread + OWN event loop
```

- Telethon **must** stay on a daemon thread. It used to be an `asyncio.create_task`
  on PTB's loop; PTB cancelled it and `CancelledError` is a `BaseException`, so the
  `except Exception` reconnect loop never caught it and signals were silently missed.
- Cross-thread work goes back to PTB via `asyncio.run_coroutine_threadsafe(coro, ptb_loop)`.
- `bot.py` line 2 **must** stay `asyncio.set_event_loop(asyncio.new_event_loop())`
  before any import — `eventkit` (ib_insync dep) calls `get_event_loop()` at import time.

## 4. Hard-won IBKR rules — do not violate

1. **Never call `reqAllOpenOrders()` on a short-lived connection.** It adopts other
   clients' orders into that session; disconnecting then cancels them all.
   Use `reqOpenOrders()` while connected as the *same* clientId that placed them.
2. **Cancel/modify must use the same clientId that placed the order.** Cross-clientId
   order operations are silently ignored by IBKR.
3. **Always `reqMktData(..., snapshot=True)`.** Streaming (`snapshot=False`) creates a
   persistent server-side market-data lock → `Error 10197 competing live session`
   accumulates across connections.
4. **Index options (SPX/NDX) must request market data over `exchange="CBOE"`.**
   `SMART` routing triggers 10197 even with nothing else connected. Qualification via
   SMART is fine — only the *data request* needs CBOE.
5. **Limit prices must be a multiple of the contract's `minTick`** or IBKR rejects with
   Error 110. SPX is 0.05/0.10, not 0.01.
6. **Order rejection reasons arrive via `ib.errorEvent`, not `trade.log`.** Subscribe,
   sleep ~6s, unsubscribe. Filter farm noise (2104/2119/2158…) and 10349 (TIF=DAY).
7. **One live market-data session per IBKR account.** If the account is logged in on
   mobile/TWS, the API gets no data. This is operational, not a code bug.

## 6. Session 11 code review — what was fixed

All fixed, deployed, and compiling on the VPS.

| # | Severity | Bug | Fix |
|---|---|---|---|
| 1 | **Critical** | `bot.py` CONFIRM state had an **unpatterned** `CallbackQueryHandler` — tapping *any* other inline button (signal/login) while an order confirmation was open fell through and **placed the order** | added `pattern=^(confirm\|cancel\|change_price)$`; also patterned OPTION_TYPE |
| 2 | **Critical** | Closing a **short** position hardcoded `action="Sell"` → *doubled the short* instead of closing | action now derived from position sign (`Buy` to close a short); summary + prompt updated to match |
| 3 | High | `_parse_qty` returned `None` for negative positions → `all` / `50%` silently failed on shorts | uses `abs(position)` |
| 4 | High | Limit prices never snapped to tick size → Error 110 rejections (esp. SPX) | `_min_tick()` from `reqContractDetails` + `_round_to_tick()` applied to place *and* modify |
| 5 | High | `_get_pending_orders_sync` still used `reqAllOpenOrders()` on a short-lived connection (violated rule #1; fixed in cancel/modify back in session 6 but missed here) | connects as base clientId, uses `reqOpenOrders()` |
| 6 | Medium | `ord_select` parsed callback index unguarded → `IndexError` crash | defensive parse, same as the positions fix |
| 7 | Medium | Listener spun forever if `SIGNAL_CHANNEL` unset; leaked a Telethon client per reconnect | explicit guard + `disconnect()` in `finally` |
| 8 | Medium | Ticker regex took the first 1–5 letter word → a date-first OCR layout yielded ticker `JUN` | skips month names / CALL / PUT / etc. |

**Verified after the fixes:** all 4 real signal samples still parse correctly, the
date-first edge case now yields `TSLA`, tick rounding produces valid multiples for
0.01/0.05/0.10, short-position qty resolves, and bot restarted with **0 errors**.

## 6b. Risk guards (added session 11)

**Kill switch — built into `sleep`.**
- `sleep` writes a flag file `.trading_halted` at the project root **and** stops the gateway.
- While the flag exists, **every order-placing path refuses**: manual confirm, signal
  order, position close, and modify (modify is cancel+replace, so it places).
- Plain **cancel is still allowed** — it only reduces exposure.
- The check runs **before `_ensure_gateway()`**. This matters: `_ensure_gateway` restarts
  the gateway on demand, so a naive check placed after it would let an order through
  even though the bot was "asleep". That was the pre-existing hole.
- The flag is a **file, not memory** → a halt survives a bot restart, and you can trip or
  clear it from the shell (`touch` / `rm` `.trading_halted`).
- Cleared by `wake up` and by a successful `login`.

**Position size cap.**
- `MAX_CONTRACTS_PER_ORDER` in `.env` (**default 50** if unset).
- Enforced in two layers:
  1. Handlers — friendly Telegram message naming the qty, the cap, and the share count.
  2. `_place_order_sync` in `ibkr/client.py` — a hard backstop that rejects **before
     connecting to IBKR**, so no code path (including future ones) can bypass it.
- Rationale: options are ×100. `10` → `100` is one keystroke, and this account has
  already filled 150- and 343-contract orders, so the blast radius is real.

## 7. Known-open items (not bugs I introduced — decide before scaling up)

- **⚠️ Live trading is still UNPROVEN end-to-end.** Everything is validated on paper
  (port 4002). Switching to live (4001) via `login` has never been run through to a
  real fill. Do a dry run: `login` → Live → verify the account summary shows the real
  account → place **one** cheap far-OTM contract → close it.
- **⚠️ The login page is served over plain HTTP.** Credentials cross the internet in
  cleartext. Fine-ish for paper; for a live account this should be TLS (or an SSH
  tunnel / bind to localhost). Port 7823 is confirmed reachable externally.
- **`_get_pending_orders_sync` change needs a live check** — view `pending orders`
  while an order is actually working and confirm (a) it lists, (b) it still exists
  afterwards. This is the one fix whose failure mode is "list shows nothing".
- **VPS-only paths are hardcoded** in `handlers.py` (`/root/IBC/config.ini`,
  `/root/restart_gateway.sh`, `/root/bot/.env`) — the login flow can't run locally.
- **No structured logging / audit trail of placed orders.** Everything is in
  `bot.log` as ib_insync dumps. An orders CSV/JSON ledger would be the obvious V2 item.
- **`_gateway_up()` does a substring match** on `ss -tlnp` output (`":4002" in stdout`)
  — could false-positive on another port containing that string.
- **No daily loss limit.** The kill switch and size cap exist (§6b), but nothing trips
  them automatically. A P&L-based auto-halt is still the missing piece — it's the one
  that would protect the account overnight, when signals arrive on someone else's clock.
- **Session 11 fixes + guards are deployed and live** (bot in tmux session `bot`,
  `MAX_CONTRACTS_PER_ORDER=50` in the VPS `.env`, 0 errors on startup). Still worth a
  manual Telegram smoke test: `sleep` → attempt an order (must refuse) → `wake up`.

## 8. Fast orientation commands

```bash
# is it alive?
ssh root@<vps> "pgrep -af 'python3 bot' | grep -v bash"

# what's it doing / any errors since last start?
ssh root@<vps> "tail -40 /root/bot.log"
ssh root@<vps> "grep -E 'Traceback|IndexError|ERROR' /root/bot.log | tail -20"

# gateway up? which mode?
ssh root@<vps> "ss -tlnp | grep -E ':400[12]'"     # 4002=paper 4001=live

# restart — use tmux, NOT `nohup ... &` over SSH.
# A backgrounded process started directly by an SSH command dies when the
# session closes; the bot looks restarted but is actually gone.
ssh root@<vps> "tmux kill-session -t bot 2>/dev/null; tmux new-session -d -s bot 'cd /root/bot && python3 bot.py >> /root/bot.log 2>&1'"
```

**Local syntax check before every deploy:**
```bash
py -m py_compile bot.py signal_parser.py tg/*.py ibkr/*.py
```

**Deploy (run when the VPS is reachable):**
```bash
scp bot.py signal_parser.py root@<vps>:/root/bot/
scp tg/handlers.py tg/messages.py tg/signal_listener.py root@<vps>:/root/bot/tg/
scp ibkr/client.py root@<vps>:/root/bot/ibkr/
ssh root@<vps> "grep -q MAX_CONTRACTS_PER_ORDER /root/bot/.env || echo 'MAX_CONTRACTS_PER_ORDER=50' >> /root/bot/.env"
ssh root@<vps> "cd /root/bot && python3 -m py_compile bot.py tg/*.py ibkr/*.py && echo OK"
ssh root@<vps> "pkill -f 'python3 bot.py'; cd /root/bot && nohup python3 bot.py >> /root/bot.log 2>&1 &"
```
Then smoke-test in Telegram: `sleep` → try an order (must refuse) → `wake up` → order works.

## 9. Working agreements (from the user)

- Deploy = `scp` the changed file(s) to `/root/bot/...` then restart the bot.
- Don't change working local scripts unless asked.
- Secrets never go in git — verify with `git add -A --dry-run` before committing.

  *did* work — re-check with a short follow-up command instead of assuming failure.

## 10. If you're starting a V2

Highest-value next steps, in order:
1. **Prove live** (dry run above) — nothing else matters until this is done.
2. **TLS or tunnel for the login page.**
3. **Risk gates** — max contracts per order, daily loss limit, kill-switch command.
4. **Order ledger** — append every placed order + fill to a JSON/CSV for reconciliation.
5. **Position reconciliation on startup** — compare IBKR positions vs last known state.
